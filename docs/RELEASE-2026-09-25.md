# Audit remediation and owner payments — release candidate

This is a release candidate, not evidence of a production deployment. The inspected live vendor build was ddd6977; repository main was fe4d7f2. No production database or active-user analytics were available for this work.

## Implemented

- Owner setup tab and server guard. Payment administration requires both `dive.settings.manage` and an installation-specific server-controlled owner allowlist. Even an employee accidentally granted every application permission cannot configure merchant accounts unless the hosting operator also designates that identity as an owner.
- Stripe Connect OAuth with short-lived, single-use state. Checkout uses direct charges on the configured business account. No employee payout destination, application fee, transfer, or wallet account is accepted from payment requests.
- Stripe card/eligible Apple Pay checkout; dockside QR/link for customers' own phones. This is web checkout, not NFC Tap to Pay or Stripe Terminal hardware integration.
- Venmo via the owner's PayPal business credentials, encrypted at rest. The order payee is selected on the server. USD/US provider eligibility applies. Do not configure live Venmo credentials before the reconciliation limitation below is resolved.
- Customer terms/privacy page, editable cancellation/refund/retention policies, owner policy approval, and checkout acceptance. Actual legal business details and policies are intentionally not invented.
- Local diver roster creation, assignment, and completion attribution. An EOS workspace login invitation is still a separate platform-admin action; adding a roster entry sends no email and creates no login.
- Completion/POS idempotency, occurrence checks, immutable completion answers/proof/pay snapshots, stock and cash validation, optimistic job edits, record archiving/restore, calendar validation, timezone display, and truthful email-draft status.
- Payment webhook signature verification, replay protection, amount/account matching, and Stripe refund ledger deltas. Payment/sale ledger entries cannot be deleted through the ledger UI/API.
- Updated dependencies, health proxy routes, and CI with PostgreSQL migration/integrity checks. Production npm audits reported zero known vulnerabilities at verification time. Development-tool findings may remain.

## Hosting setup

Use the existing EOS Lightsail hosting path described in DEPLOY.md; no replacement production site was created. The deploy operator needs the EOS hosting-ops repository, host access and existing production environment. Take and verify a production database backup before migrations; test against a restored copy first. Do not seed production.

Runtime configuration (secrets belong in the hosting secret store, never this repository or chat):

- `PAYMENT_OWNER_IDS_JSON`: map installation IDs to verified owner user IDs, e.g. `{"inst_example":["usr_owner"]}`. The hosting operator verifies the actual owner before setting this. No employee-facing API can change this mapping. Designated owners also need `dive.settings.manage` from EOS.
- `PUBLIC_APP_URL`: canonical HTTPS public vendor app origin, accessible outside the authenticated EOS iframe.
- `STRIPE_SECRET_KEY`, `STRIPE_CONNECT_CLIENT_ID`, `STRIPE_WEBHOOK_SECRET`: matching Stripe platform environment. Enable Standard Connect OAuth and register `PUBLIC_APP_URL/api/admin/payments/stripe/callback`. Connect the owner's business account in Owner setup.
- Stripe connected-account webhook endpoint: `PUBLIC_APP_URL/webhooks/stripe`, events `checkout.session.completed`, `checkout.session.async_payment_succeeded`, `charge.refunded`. Configure events for connected accounts, not only the platform's own charges. Configure business terms URL in Stripe as required for hosted Checkout consent.
- `PAYMENT_ENCRYPTION_KEY`: securely generated 32 random bytes encoded as base64. Back it up securely; rotating it without re-encrypting saved credentials breaks Venmo. Enter the owner's PayPal REST credentials in Owner setup. `PAYPAL_ENV` defaults to sandbox; use `live` only after provider testing and reconciliation work.
- Existing EOS/JWKS/bridge configuration, frame origins, DB settings and HMAC webhooks remain required. Never enable any `USE_DEV_*` flags in production.

Only the owner should approve the business identity and actual policy text in the app. These templates are not a determination of legal compliance or a dive liability waiver. Applicable jurisdiction, legal entity, tax treatment and required waivers were not provided.

## Required before enabling live payments

1. Test real Stripe sandbox Connect, customer checkout, duplicate webhook delivery, refund, cancellation and timeout recovery. Test Apple Pay on an eligible real device and the public QR URL outside EOS.
2. Complete PayPal/Venmo sandbox tests with the owner's account. **Venmo currently reconciles successful capture via the customer callback or Check payment action. A verified PayPal webhook/reconciliation worker for abandoned callbacks, refunds and disputes is not yet implemented. Keep Venmo sandbox-only until that is added and tested.** An abandoned Venmo order also currently blocks switching that invoice back to Stripe.
3. Confirm merchant ownership, deposit destination, currency and settlement in provider dashboards. Fees, refunds, reserves and provider payout timing apply; “direct to owner” does not mean immediate bank settlement.
4. Approve real business policies, final tax-inclusive service amounts, data retention and any required waiver with qualified local review.
5. Verify roles using real EOS identities, not dev tokens. Owner allowlist revocation and settings permission revocation must both hide/deny setup.
6. Reconcile pre-existing paid services before creating links; existing records do not tell us reliably which services were already paid offline. Avoid charging customers twice.

## Data migration and validation

The additive migration adds snapshots, occurrence uniqueness, roster fields, archive flags, receipts, audit/payment/settings tables. Legacy record pay is frozen using the *current pre-upgrade rate* and labeled `legacy_baseline`; this does not recover unavailable historical rates. Reconcile historical payroll before payout. Old duplicate records are not silently deleted.

Local validation: API build, Next production build, disposable PostgreSQL-compatible PGlite migration, integrity tests, and HTTP access tests. PGlite serializes connections; it does not prove real PostgreSQL concurrent transaction behavior. CI runs the migration and integrity suite against PostgreSQL 16. Docker image build, real EOS authentication, production data migration, provider sandbox checkout, and production rollout require the operator environment and are not claimed as completed.

## Open audit/feature items

The app is not certified bug-free. Remaining items include platform team invitation/account linking, genuine server-side email delivery tracking, payroll locking/adjustments and rate history, pagination of long-lived data, full uninstall/write-race coverage, offline draft recovery, payment disputes/fees/tax reporting, provider reconciliation, real-device accessibility/checkout checks, and production monitoring/restore drills. Existing service values and ledger cash are now separate; the ledger is not a complete accounting system.

After a successful rollout, verify `/healthz`, the served build SHA, real owner/diver journeys and data totals. Keep the prior image and DB snapshot for rollback. Never assume a successful dry-run deployed: existing hosting scripts require their live-deploy flag and post-deploy verification.
